# 证据分析与待核事项

更新：2026-11-07。协议：`evidence-filtered-v6`。

## 用户步骤

1. 在「类案」页筛选、分析并保存本案的类案结果，移出不相关案例。
2. 打开「证据分析」。先展示上述已保留结果，按案号去重，默认勾选前三案；不足三案时全部勾选。可核对原文、取消或更换，每轮 1–5 个案件。零案不能开始。类案条件、来源资料或列表版本有变化时要求刷新或重新分析。
3. 点击开始。逐案独立分析证据，全部完成才汇总；显示逐案进度、失败恢复入口和精确来源。重新分析保留旧成果。
4. 汇总展示「已有证据与材料」「建议补充或核对的证据」（具体证据、为何需要、获取渠道、下一步）和「待核问题」。问题合并去重，最多十项；每项仅一句问题和一句「为何重要」，各不超过 60 字。来源中提及证据不代表已经上传该证据原件。
5. 在本页追问证据。追问固定所依据的分析版本，使用该版来源与最近问答；后台任务持久执行，刷新后可查看。回答带来源，不触发新一轮类案分析。同一分析一次只生成一条回答。
6. 生成 Word 并保存。正文仅包含「已有证据与材料」「建议补充或核对的证据」（三列表格：证据、获取渠道、为何需要）和「待核问题」（问题与简短原因）；不附逐案分析、追问记录、来源索引、下一步或分析范围说明。在「材料中心 → 文书与研究文档」独立区域按生成时间显示、下载。文件名带生成时间及时区，对应版本保存在归档记录中。每次新生成保留独立文件；幂等重试不重复归档。

## 来源与执行

新分析读取 `similar_cases` 的成功结果和筛选条件，扣除已移出的文书。请求冻结结果版本、条件、语料、候选及选择；不执行另一套未筛选检索。排队后的任务保持该快照，不被后续类案编辑覆盖。材料变化仍通过既有案件版本与取消机制阻止旧任务继续。

每个单案请求只含该篇判决及原文片段，不含其他判决或客户案情。每篇最多 6,500 字，每案至多三个证据要点，长文披露节选范围。证据名来自原文；「采信/不采信」须有逐字相同、包含证据名和法院评价的原句，否则记为「无法确认」。引用程序检查不替代内容复核。

单 worker 内部最多两个逐案请求在途，等待全部响应后统筹。默认三案证据阶段为三次逐案请求加一次统筹请求（手动选五案则为五次逐案请求加一次统筹请求），首次材料整理可能另有调用。综合输出为每个选定案例设置一个必填证据任务，每项引用只能来自对应案例，再统一生成补证清单。逐案完整报告仍保留原文；汇总模型仅接收类案的中性证据类型及评价状态，避免将其中的姓名、合同名称、金额和日期混作本案事实。全部选定案例都必须被汇总引用。材料摘录受上下文预算约束，遗漏范围明确披露。

失败保存成功逐案结果，恢复时仅重做未完成项。每案和统筹各至多两次尝试。包含证据分析的任务保持 32 次模型调用、1,800 秒活跃执行预算；追问为独立任务，采用通用预算。协议更新后的旧未完成分析需要新建任务，已有成果仍可查看。

## 存储与访问

- `evidence_batches`、`evidence_agents` 保存逐案范围、结果和恢复状态。
- `artifacts` 保存综合分析，`evidence_answer` 类型保存回答和对应 `evidence_artifact_id`。
- `runs.snapshot.evidence_context` 冻结追问的分析、来源和最近对话。
- `reference_documents` 原子保存 Word 字节、名称、生成时间、内容哈希、分析及回答 ID。文档不会写入 `materials`，不会改变案件资料版本或类案状态，也不会成为新的证据输入。
- 创建参考文档检查当前资料、内容和精确来源，文档明确为待核对参考资料；不要求先执行正式文书的复核导出步骤。
- 归档文件保留历史版本；资料变化后标为历史参考。来源撤回、内容被标记不通过或案件删除后停止下载。所有接口复用案件访问权、会话和写操作 CSRF 校验。

## 接口

```json
POST /api/v1/cases/{case_id}/requests
{
  "workflow":"evidence.gaps",
  "goal":"逐案分析并汇总证据与待核事项",
  "evidence_selection":{"similar_version":3,"doc_ids":["真实候选文书ID"]}
}
```

`evidence_selection` 省略时仍只使用当前类案页的有效结果，默认取前三个不同案件。旧 `evidence_review` 请求保留兼容性，但所选案例也必须仍在当前类案结果中。

```json
POST /api/v1/cases/{case_id}/requests
{
  "workflow":"evidence.followup",
  "goal":"为什么需要核对这份证据的原件？",
  "evidence_artifact_id":"art_分析版本ID"
}
```

`GET /api/v1/runs/{id}/evidence` 读取逐案进度。案件详情的分析成果含规范化 `evidence_view`，`follow_up_details` 包含 `question` 和 `why_matters`，同时保留 `follow_up_questions` 字符串列表。历史成果无需改写也可展示简短问题与原因，待核问题始终最多十项。

```json
POST /api/v1/artifacts/{id}/reference-documents
{
  "content_hash":"当前分析内容哈希",
  "timezone":"America/New_York"
}
```

该写接口及任务创建接口均要求 `Idempotency-Key`。旧客户端的 `include_answers` 字段仍可接收，但证据 Word 不再附带追问，归档的回答数量为零。案件详情返回 `reference_documents`，下载入口为 `GET /api/v1/reference-documents/{id}/download`。

## 验证

```sh
.venv/bin/python -m pytest -q --junitxml=evaluation/evidence-workspace-tests.xml
npm --prefix frontend run build
```

`tests/test_evidence_agents.py` 检查隔离逐案请求、等待全部响应、失败与恢复及来源校验。`tests/test_evidence_workspace.py` 检查筛选一致性、1–5 案约束、移出与版本冲突、最多十个问题、追问持久化和上下文、未知引用拒绝、Word 内容、时间戳、幂等归档、材料隔离及访问撤回。模型替身仅用于隔离测试，不作为实际法律内容验收依据。旧 v1–v4 验收记录仍保留在 evaluation，不能作为本次界面验收记录。
